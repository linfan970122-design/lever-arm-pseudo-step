## 0. Frame selection

**Replays are excluded.** Recordings whose `/rtk_odom` time stamps duplicate another recording are replays of that recording, not independent data, and are dropped from every statistic here. One recording qualifies — `orchard3src_20260826_2026-08-26-10-02-59`, whose frames are stamped in the same 14-minute window as `orchard_20260826_2026-08-26-08-31-44` — removing 4200 frames. The detection is in section 8.

**Gyro spikes are removed at a fixed threshold.** Every use of the CH110 in this file — the physical bound of §3, the straight/turn labelling, the genuine/outlier scoring of §7 and the drift measurement behind `gyro_drift_rate` — drops samples with |ω_z| > 5 rad/s (286 °/s), the same rule as `data/post_summary.py`. Three samples in the corpus exceed it, the largest by seven orders of magnitude; nothing else is filtered.

A *frame* is one `/rtk_odom` message (5 Hz); an *increment* is the pair (k−1, k). An increment enters the statistics only if
1. both frames carry a heading (`cov[35] < 1e5`; without a heading the driver publishes yaw = 0 **and skips the lever-arm rotation**, so such an increment is an artefact, not a heading outlier), and
2. the two frames are less than 0.5 s apart (no recording gap).

## 7. Gate sweep (Fig. 6 / Fig. 7 / Table 4)

Three rules are replayed, all through `fig/gate.py`, all with the same parameter names. **v1** is the rule as patched today: `budget = max_yaw_rate·dt + yaw_gate_margin`, dt measured from the last *accepted* heading and unbounded. **v2** bounded that dt at `max_hold_frames·nominal_dt`, stopped publishing once a hold was exhausted, and re-anchored on two mutually consistent samples. **v3** is the specification that goes into the C++ patch: the budget does not scale with dt at all, a reference older than `max_gap_frames` is declared stale, and re-anchoring is done against the gyro-propagated heading (rule **a**) or, where no IMU is present, against two consistent samples (rule **b**).

```
params: max_yaw_rate, yaw_gate_margin, nominal_dt = 0.2 s, max_hold_frames = 5,
        max_gap_frames = 3, gyro_drift_rate = 0.002 rad/s, use_gyro
state:  last_accepted_yaw, last_accepted_t, hold_count, valid, pending(yaw, t),
        gyro_yaw = last_accepted_yaw + integral of omega_z since last_accepted_t
per frame (y, t):
  g = max_yaw_rate * nominal_dt + yaw_gate_margin            # FIXED, no dt scaling
  dt = t - last_accepted_t > max_gap_frames * nominal_dt and valid
        -> valid = false, pending = None                     # stale reference
  valid:
     |wrap(y - last_accepted_yaw)| <= g -> ACCEPT (publish y, hold_count = 0)
     else -> HOLD (publish last_accepted_yaw, hold_count += 1)
             hold_count >= max_hold_frames -> valid = false, pending = None,
                                              frame NOT published
  not valid: nothing published; re-anchor
     (a) use_gyro and gyro available:
         |wrap(y - gyro_yaw)| <= g + gyro_drift_rate*(t - last_accepted_t)
             -> ACCEPT y (valid = true); else stay invalid
     (b) otherwise: pending is None -> pending = (y, t)
         |wrap(y - pending.yaw)| <= g -> ACCEPT y (valid = true)
         else -> pending = (y, t)
```

The re-anchoring frame is itself published (it is an ACCEPT); the count of re-anchor events is reported so that a stricter reading, publishing only from the following frame, can be derived without re-running.

A sweep point *g* is the per-frame budget, g = max_yaw_rate·τ + yaw_gate_margin with τ = 0.2 s, `yaw_gate_margin` at the deployed 0.05 rad and `max_yaw_rate` carrying the rest (below g = 5.73° the margin is halved to g/2 so that `max_yaw_rate` stays positive). In v3 this budget is what the frame is compared against directly, at every frame, whatever dt is.

A frame is scored against the IMU: **genuine** if |wrap(Δψ − Δψ_IMU)| ≤ 2.0° (the gyro confirms it, so not accepting it is a false trip), **outlier** otherwise; frames from the 7 recordings without an IMU carry no label and are excluded from both rates. The false-gate rate counts genuine frames that were **held or withheld**; a pseudo-step frame counts as **caught** when the reported heading was not accepted — held or withheld, either way it never rotates the lever arm.

### Where gyro_drift_rate comes from

`gyro_drift_rate` is the allowance rule (a) adds to the budget while the heading is withheld, to cover MEMS bias in the propagated reference. It is set from the data: on contiguous straight, fixed-solution stretches, the gyro-integrated heading change over 60 s is compared with the HDT heading change over the same window.

### What the remaining misses actually are — the dt scaling was not the cause

v2 still missed 5 of the 36 pseudo-step frames at g = 17°, with frame-to-frame |Δψ| of 16.6–62.7°, and the working hypothesis was that the dt-scaled budget let them through. **The replay says otherwise.** v3 removes the dt scaling completely and misses the same 5 frames under rule (b) (11 under rule (a)). ### The metric that decides it: what is left in the output

Counting frames the gate refuses is the wrong measure, because refusing a frame does not remove the step — it moves it to the edge where the gate takes a heading back. So the output of every rule is rebuilt, p_gated = p_ant − R(ψ_gate)·L with ψ_gate the heading that rule actually uses (accepted → as reported, held → the last accepted, withheld → no output, so the next published frame is differenced against the last published one), and the pseudo-step definition is applied to **that** stream: fixed solution, heading valid, antenna point still to within 0.02 m over the same interval, step at or above the threshold. ### 9.4 Motion classification, v1 → v2

🔴 Reviewer 3 is right: the v1 *slow* test used the published displacement over the trailing window, i.e. the quantity a lever-arm pseudo-step corrupts. The rule is now, verbatim (`fig/motion_class.py`):

```
W = 3.0 s                              trailing window
d_ant_win = sum |dp_ant| over (t-W, t]  reconstructed antenna path
turn_win  = integral omega_z over (t-W, t]        IMU only
d_ant_win <= 0.50 m         -> slow
else |turn_win| < 5.0 deg   -> straight
else                        -> turn
less than W of history, or no IMU in the recording -> na
```

Only the *slow* test changed; straight/turn is the same IMU integral as before. **172,769 frames (47.4 %) changed class**, almost all of them from v1 straight or turn into v2 slow (129,158 and 32,256 frames) — the v1 rule had no slow class at all for IMU-labelled frames, so every stationary frame was being counted as straight or turn.

### 9.5 A normalised-innovation gate instead (Reviewer 2)

🔴 **This is a 1-D emulation, not the full `robot_localization` filter**: one scalar yaw state, no cross-covariance with position or velocity, no differential-drive process model. It answers one question — would a chi-square test on the innovation have caught these? — and nothing else. Prediction is the gyro increment (the yaw is held where there is no IMU), P grows by q·dt with q = (0.002 rad/s)² = 4.0e-06 rad²/s from the measured gyro drift, R = 7.62e-05 rad² is the cov[35] the driver publishes (0.50°), and a heading is rejected when ν²/(P+R) > k². On rejection the state and P are not updated, so P keeps growing and the test loosens by itself.

|---|---|---|---|---|---|---|---|
| 3 | all | 19.31 | 84,159 | 0 | 14 / 21 | 0 | 10 |

| 5 | all | 14.56 | 66,182 | 0 | 13 / 21 | 0 | 12 |

Read both columns. The innovation test is the **only** rule tested that leaves zero residual pseudo-step episodes ≥ 0.10 m in its own output — because it never publishes the measurement, it publishes a filtered estimate, so a heading jump cannot become a position step. The price is that it rejects 17.6 % of the gyro-confirmed increments at k = 3 (13.6 % at k = 5), which is what taking the driver's optimistic 0.50° at face value costs when the measured σ_ψ is 0.7356° overall and 1.0923° in the greenhouses. On event 1 it rejects for 210 s and comes back 14.1° off (0.089 m of published position error) at k = 3.

### 9.6 Position-test ROC — what is missing and how to get it

🔴 **Not run: the inputs are not in this corpus, and nothing is fabricated here.** The two deployed position-domain tests are replayed by the guard replay script of the 2026-09-09 orchard session (not distributed), which imports the judgement verbatim from the deployed `guard_watch.py`. Their inputs are

| test | class | topics it must be fed |
|---|---|---|
| cross-track | `LatSentinel(win=3.0, thresh=T, persist=1.0, min_disp=0.5, max_dhdg=5.0, hold_s=5.0)` | `/rtk_odom` → `feed_rtk`, `/rtk/status` → `feed_hdg` (HDT, 1 Hz, fixed solution only), `/smoother_cmd_vel` + `/nav_cmd_vel` → `mark_auto` |
| chord | `DispSentinel(win=3.0, thresh=T, hold_s=5.0)` | `/rtk_odom` → `feed_rtk`, **`/odom` (wheel odometry)** → `feed_odo`, `/rtk/status` → `set_fix` |


`data/extract_p2.py` pulled only `/rtk_odom`, `/rtk/status`, `/rtk/fix` and the IMU topic, so the CSVs on this machine carry **neither `/odom` nor the two cmd_vel topics**. Consequences:

* the **chord test cannot be replayed at all** here — its whole point is RTK against wheel odometry, and the wheel odometry is not in the extract;
* the **cross-track test could be fed** position and heading from the CSVs, but `LatSentinel.step()` only evaluates while `t_end <= auto_until`, i.e. while a non-zero command was seen in the last 2 s. Without cmd_vel the evaluable set — which is the denominator of any false-alarm rate — would be a different set from the deployed one, so the ROC would not be the deployed criterion's ROC. A false-alarm rate measured over the wrong denominator is worse than no number.

What is needed to produce it, on the industrial PC where the bags and the deployed sources are:

```
# on the industrial PC
export GUARD_SRC=$HOME/fusion/safety        # dir holding the deployed guard_watch.py
python3 roc_position_tests.py \
        --bags operational_baglist.txt \
        --onsets pseudo_steps.csv \
        --out position_roc.csv
```

`fig/roc_position_tests.py` is written and committed for exactly this: it imports `LatSentinel` and `DispSentinel` from `$GUARD_SRC` (never re-implementing the judgement), feeds them the same topics `replay_guards.py` does, steps them at 10 Hz, sweeps the cross-track threshold over 0.05 / 0.10 / 0.15 / 0.20 / 0.30 m and the chord threshold over 0.10 / 0.20 / 0.30 / 0.50 m, and writes alarms, evaluable hours, false alarms per evaluable hour, and pseudo-step onsets detected (matched within ± 5 s against the onsets in `pseudo_steps.csv`). It needs two files copied over: `pseudo_steps.csv` and a list of the 46 operational recordings — the 2026-09-06 15:26 induction session must be left out of that list.

Until it is run there, the only position-domain statement this corpus supports is the geometric one already in §4: of the 21 operational frames stepping ≥ 0.10 m, 4 exceed the deployed 0.30 m cross-track threshold and 1 the 0.50 m chord threshold — which bounds what any replay can find, because a test cannot alarm on a step smaller than its own threshold.
